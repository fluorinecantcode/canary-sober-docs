Architecture

Threading and data model. Single-writer each; no torn config.

Snapshot vs EntitySnapshot​

  • EntitySnapshot: one player — joints Vec3[13], jointCount (7 R6 / 13 R15), valid.
  • Snapshot: one frame — {CameraView cam, Vec<EntitySnapshot> entities, uint64 tickId, Config config, float fbScale, Vec2 viewport}.
  • Matrix + viewport + fbScale travel together per Snapshot (no read/render race).

Store ownership​

  • Read thread owns the Snapshot store: std::atomic<std::shared_ptr<const Snapshot>>, single store.
  • Render thread owns Config staging edits (menu), publishes via MPSC queue<Config> drop-stale, latest-wins, capacity 1.
  • Read thread applies the latest Config then stores the {config, snapshot} PAIR atomically (one store, no torn-config).
  • Render loads the pair locally; null at startup → idle screen.
  • valid is reader-only: set on staleness > 80 ms wall-clock; render never clears it. Render-side W2S failure skips draw only.
  • W2S runs on the render thread only; the read thread caches world positions + matrix.

IFeature​

struct IFeature {
  virtual void update(const Snapshot& in) = 0;
  virtual void drawOverlay(const Snapshot& in) const = 0;
};

update consumes (ESP culls); drawOverlay renders and is const. ESP implements both. No aimbot code (grep gate).

Entity handles: 750 ms single. Positions/health/bones + matrix every read tick. Maps cache TTL 5 s keyed (pid, starttime field 22).
